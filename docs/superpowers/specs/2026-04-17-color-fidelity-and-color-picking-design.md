# Color Fidelity and Color Picking Separation Design

Date: 2026-04-17
Project: macshot
Status: Approved pending written spec review

## Summary

当前 macshot 在截图链路里主动把画面统一到 `sRGB`，这样做有一个明显好处：吸管、十六进制颜色值、导出后的颜色数值更稳定，更容易和常见网页颜色系统对齐。

但这个策略也带来了一个用户可见问题：当用户把截图固定回原来的屏幕内容上，尤其是在纯色背景、广色域显示器、或者对比边缘很干净的区域，截图会和原背景出现肉眼可见的色差。边框、阴影、圆角只是把这个问题暴露得更明显，并不是色差的根因。

本次方案采用“双通道”设计：

- 显示链路保留原始颜色信息，优先保证“看起来和原屏一致”
- 取色链路单独维护标准化副本，优先保证“取色数值稳定”

这样可以同时满足两个目标：

- 固定窗口、编辑器预览、无装饰显示尽量贴近原屏视觉效果
- 吸管、十六进制、需要标准色值的后续流程继续保持稳定

## Goals

- 让固定窗口在原始屏幕内容上尽量做到无缝贴合
- 让编辑器和预览链路优先显示保真颜色
- 保留现有取色稳定性，不让十六进制颜色值因为屏幕色域而变得不可预测
- 把性能成本控制在可接受范围内，避免每次截图都同步生成多份大图
- 为后续“导出保真”和“导出标准化”预留清晰边界

## Non-Goals

- 本次不重做整套导出格式设置界面
- 本次不引入新的颜色管理面板或高级专业色彩设置
- 本次不尝试解决所有第三方应用中的色彩显示差异
- 本次不把吸管扩展成双模式 UI，只先把内部链路拆清楚

## Problem Statement

现有代码把“显示一致”和“取色一致”绑定在同一条链路上：

- 截图时显式请求 `sRGB`
- 后续又把图转成 `8-bit BGRA + sRGB`
- 固定窗口和编辑器显示的，已经不是最初的显示用原图，而是经过标准化处理后的图

这意味着：

- 对用户来说，看到的是一张更适合“取数值”的图，而不是更适合“贴回原屏”的图
- 纯色背景最容易暴露这种差异
- 隐藏边框、阴影、圆角后，视觉注意力集中到图像本体，色差会更明显

## Design Principles

### Principle 1: Separate Visual Fidelity From Numeric Stability

“看起来一样”和“取出来的 RGB 数值稳定”不是同一个目标。系统不能再要求一张图同时完美承担这两个职责。

### Principle 2: Keep The Fast Path Cheap

用户最频繁的路径是：

- 截图
- 立即预览
- 固定到屏幕
- 简单编辑

这些路径应该优先使用显示底图，不应该为了取色提前付出整张图标准化的成本。

### Principle 3: Create Standardized Data Lazily

标准化副本只在真正需要的时候生成，例如：

- 吸管第一次读取颜色
- 需要标准颜色值的某些导出场景

如果用户只是截图、固定、查看，那么不应额外生成第二份完整大图。

## User-Facing Behavior

### Pin Window

- 固定窗口默认显示保真底图
- 当关闭边框、阴影、圆角后，图像本体仍使用保真底图，不再切回标准化副本
- 在原屏纯色背景上，截图与背景的贴合程度会明显提升

### Editor Preview

- 编辑器中看到的底图使用保真底图
- 标注、框选、预览行为不改变
- 用户看到的画面更接近原屏，而不是更接近标准化色值

### Color Picker

- 吸管不从显示底图读值
- 吸管从标准化副本读值
- 十六进制和 RGB 数值行为保持稳定，与现有“按标准值取色”的方向一致

### Export

- 本次先保持现有导出行为整体可用
- 内部架构上明确区分“显示用底图”和“标准化底图”
- 后续如果要支持“保真导出”与“标准化导出”切换，可以在这次拆分基础上继续演进

## Proposed Architecture

### Two Image Roles

每次截图后，系统内部明确持有两种职责不同的图像引用：

| 图像角色 | 作用 | 何时生成 |
|---|---|---|
| `displayImage` | 给固定窗口、编辑器、预览、无装饰显示使用 | 截图后立即可用 |
| `colorAccurateImage` | 给吸管、十六进制、标准化颜色读取使用 | 按需懒加载 |

这两个名字只是设计层概念，实际命名可按现有代码风格调整，但职责必须保持清晰。

### Capture Layer

截图模块不再把“显示用图像”默认压到统一标准色空间。显示底图应尽量保留系统给到的原始图像信息。

标准化处理不再作为显示链路的前置步骤，而是作为取色链路的派生步骤。

### Overlay Layer

`OverlayWindowController` 和 `OverlayView` 需要明确知道：

- 当前展示给用户看的底图是哪一份
- 当前吸管、放大镜、颜色读取应该基于哪一份图

现有 `originalCGImage` 这类字段可以沿用，但职责要重新定义，避免“显示底图”和“取色底图”继续混在一起。

### Pin Window Layer

固定窗口只应消费显示底图，不应在切换装饰时触发任何颜色标准化逻辑。

窗口装饰开关只改变：

- 圆角裁切
- 边框描边
- 窗口阴影

不能影响图像本身的数据来源。

### Encoding Layer

导出层未来需要支持两类来源：

- 保真来源：更接近用户眼前所见
- 标准化来源：更接近稳定色值输出

本次不强制把所有导出交互做成双选项，但编码层接口要避免继续假设“只有一张图”。

## Data Flow

### Fast Path: Display

1. 截图完成
2. 生成显示底图
3. 预览、固定窗口、编辑器直接使用显示底图
4. 如果用户从不取色，就不生成标准化副本

### Lazy Path: Color Picking

1. 用户第一次触发吸管或需要稳定颜色值的操作
2. 系统检查标准化副本是否已存在
3. 如果不存在，则在后台生成标准化副本
4. 生成完成后，后续取色全部复用这份副本

### Cleanup

- 关闭 overlay、编辑器或固定窗口时释放对应的标准化副本引用
- 不在全局永久缓存所有标准化大图
- 历史记录中如果只用于显示缩略图，不需要默认保留双份完整位图

## Performance Strategy

### Main Cost

本方案的主要成本不是首屏卡顿，而是额外内存占用。

如果同时保留两份全尺寸位图，额外成本大致等于再存一张同尺寸图片。

### Performance Constraints

- 不允许每次截图后同步生成第二份完整标准化副本
- 不允许固定窗口显示依赖后台标准化完成
- 不允许吸管每次移动都重复生成标准化副本
- 不允许历史列表默认持有双份大图

### Recommended Performance Controls

| 控制项 | 方案 |
|---|---|
| 标准化副本生成时机 | 第一次取色时懒加载 |
| 标准化副本复用 | 同一张图生命周期内复用 |
| 释放时机 | overlay / editor / pin 关闭后释放 |
| 大图策略 | 必要时优先按当前选区或当前图范围生成，而不是盲目扩整屏 |

## Native-Size Pin Window

即使颜色链路拆开，固定窗口仍然可能因为缩放显示带来第二层误差。因此本次建议把“原尺寸显示”作为同一方案的一部分。

目标：

- 固定窗口在 `100%` 缩放时尽量做到 1:1 显示
- 装饰隐藏后，不再因为窗口初始化缩放而产生额外的重绘偏差

这不是颜色问题本身，但它直接影响用户对“截图是否和原屏一致”的判断。

## Implementation Outline

### Step 1: Clarify Image Ownership

- 在截图进入 overlay 时明确分出显示底图和延迟生成的标准化底图
- 梳理当前 `OverlayView` 中哪些字段是给显示用，哪些字段是给取色用

### Step 2: Decouple Pin Window From Color Conversion

- 固定窗口只拿显示底图
- 装饰开关不再影响图像来源
- 补上原尺寸显示逻辑，避免默认缩放干扰判断

### Step 3: Rewire Color Picker To Standardized Source

- 吸管读取来源切到标准化副本
- 第一次取色时触发副本生成
- 生成期间需要有明确的回退策略，避免吸管卡死或读到错误来源

### Step 4: Prepare Export Boundaries

- 编码接口补足来源语义
- 保证未来能区分“显示保真导出”和“标准值导出”
- 本次先不强推新的用户设置项

## Edge Cases

### User Pins Without Ever Picking Colors

- 只保留显示底图
- 不生成标准化副本
- 这是最常见路径，必须保持轻量

### User Picks Colors Repeatedly

- 标准化副本只生成一次
- 吸管后续全部复用
- 不能在每次鼠标移动时重复转图

### Large Retina Captures

- 大图首次标准化时会有一次后台开销
- 需要确保 UI 不阻塞，固定窗口和编辑器仍可立即显示

### Window Snap Images With Transparency

- 对带透明角的窗口截图，同样遵循双通道规则
- 显示链路保留原始透明边缘表现
- 标准化副本只用于颜色读取，不应破坏透明边缘显示

## Testing Plan

### Manual Verification

1. 在纯色背景上截图并固定，隐藏装饰后确认截图与背景贴合程度明显提升。
2. 在广色域显示器上重复上述流程，确认比当前版本更接近原屏。
3. 不使用吸管，连续截图和固定，确认首屏速度不因为双通道方案明显下降。
4. 第一次触发吸管时，确认标准化副本在后台生成，UI 不冻结。
5. 连续多次取色，确认后续没有重复卡顿。
6. 在固定窗口中切换显示装饰，确认颜色来源不变，只改变装饰表现。
7. 放大到 `100%` 原尺寸时，确认固定窗口不会再因为默认缩放带来额外显示误差。

### Regression Checks

1. 现有编辑器标注、保存、复制、上传流程继续可用。
2. 现有窗口捕捉、透明角窗口捕捉、滚动截图不出现崩溃或空白图。
3. 吸管读数在同一台机器上保持稳定，不因显示链路改为保真而退化。
4. 内存在关闭 overlay、编辑器、固定窗口后能正常回落，不出现明显泄漏。

## Risks

| 风险 | 影响 | 缓解方式 |
|---|---|---|
| 双份大图增加内存 | 中 | 懒加载标准化副本，按生命周期释放 |
| 旧代码继续混用显示图和取色图 | 高 | 先明确字段职责，再逐条替换消费方 |
| 固定窗口默认缩放继续制造误差 | 中 | 把原尺寸显示并入同一次改动 |
| 导出来源语义不清 | 中 | 先补内部接口边界，UI 后续再扩展 |

## Recommendation

推荐按以下顺序实现：

1. 先拆清 `displayImage` 与 `colorAccurateImage` 的职责
2. 再把固定窗口切到显示底图，并补原尺寸显示
3. 最后把吸管和颜色读取链路切到标准化副本

这样可以先尽快解决用户最可见的问题，再逐步恢复并保持取色稳定性。
